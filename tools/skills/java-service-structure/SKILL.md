# Java 服务结构

仅在 Java 项目中使用，并以现有包结构和架构文档为准；本 skill 不要求项目采用特定框架或目录名。

## 1. 保持依赖方向单向

```text
controller
  -> service interface
  -> service/<domain>/impl
       -> rule / support / convert / client
       -> service/<domain>/transaction
            -> mapper

job / listener
  -> service 或专用收敛组件
```

禁止 `mapper`、`convert`、`support`、`client`、`transaction` 反向依赖用例 `impl`。
Controller 不得直接调用 Mapper，也不得自己持有锁、事务、远程编排或业务状态流转。

## 2. 按职责分配包

| 包/类型 | 负责 | 不应负责 |
|---|---|---|
| `controller`（管理端与 C 端分开） | 管理端协议、校验、数据权限入口；C 端及明确限定的匿名协议 | 发明 URL 段、持久化、UI 按钮决策、管理端数据范围 |
| `service/<domain>` 接口 | 稳定用例契约 | 框架/持久化细节、厂商 DTO |
| `service/<domain>/impl` | 顶层用例编排：上下文、权限、分支、锁、事务执行器调用 | 大字段映射、原始 SQL、厂商 HTTP、超大原子脚本 |
| `service/<domain>/rule` | 纯校验、计算、状态推导；无 I/O | Mapper、远程调用、事务 |
| `service/<domain>/support` | 可复用的领域读/查询/视图支持，有界读编排、批量补全 | 写事务、Controller 响应包装、无关通用工具 |
| `service/<domain>/transaction` | 一个明确原子写入一致性集合 | 权限、分布式锁获取、响应组装 |
| `service/<domain>/client` | 远程防腐、DTO 与错误映射 | 本地状态机、事务所有权 |
| `convert/<domain>` | 确定性 MapStruct/字段转换 | 查询、权限、时钟读取、业务写入 |
| `dal/mapper` | 查询/更新原语与 CAS | UI 过滤策略、远程补全、响应组装 |
| `dal/dataobject` | 持久化形状 | 工作流行为 |
| `model/request`、`model/response` | 对外接口形状 | 事务过程状态 |
| `model/record` | 不可变内部命令/结果/上下文 | HTTP 或持久化注解 |
| `util` | 领域无关、无状态可复用机制 | 伪装成全局工具的单点用例 |

可复用领域读模型优先放 `support`，不要用临时 `query` 包，除非已接受架构定义了专用查询模块。

### 按依赖决定规则类静态化还是 Bean

不要只看 `rule` 包名就决定。先检查构造字段、框架注解、时间/配置/国际化来源与 I/O：

| 规则形态 | 必须的形式 |
|---|---|
| 无注入依赖、无 I/O、无框架上下文、无可变状态的确定性计算/校验 | `final` 类 + 私有构造器 + 静态方法，不注册 Spring Bean |
| 依赖业务时钟、MessageSource、配置属性、Mapper、client、策略集合或其他运行时 Bean | 保持实例化并注入 |

- 业务时钟是运行时依赖，即使规则其余部分无状态；保留 Bean 注入，让测试能控制业务时间、生产保持配置的时区语义。
- 不得仅为强行静态化而把业务时钟或其他 Bean 变成方法参数。
- 不得使用静态应用上下文持有者、手动实例化 Spring 管理的规则，或给纯静态规则套 Bean 包装。
- 把纯规则转静态时，移除组件注解与所有调用方的构造注入，并跑改前/改后同一测试。
- 组合规则依赖注入的规则或时钟时，即使没有可变字段也必须保持实例化。

## 3. 决定何时提取类

有可独立命名且边界稳定的职责时才提取：

- 重复的确定性转换 -> MapStruct 转换器
- 活动/查询视图补全 -> 领域 `support`
- 纯状态/日期资格 -> `rule`
- 原子多写块 -> `transaction`
- 厂商调用/协议 -> `client`
- 领域无关的随机/时间/字符串机制 -> `util`

不要仅因方法长或"以后可能复用"就提取。需要当前调用边界、可测试职责或已确认的近期复用。

内部 `record` 或类在两个及以上组件需要同一语义上下文时移到 `model/record`；仅事务执行器内部使用的 `Command`/`Result` 保持就近嵌套。

## 4. 设计可读方法

- 每个公开方法一个用例意图，每个私有助手一个可解释步骤。
- 拒绝和缺失优先早返回，避免深嵌套。
- 编排从上到下可读：解析上下文 -> 校验 -> 加载 -> 加锁 -> 事务 -> 投影响应。
- 一个方法混合"权限、查询构造、远程补全、转换、加锁、事务、错误收敛"中两个以上职责时拆分。
- 超过三个相关值跨边界时用不可变 `record` 命令/上下文；不用 `Optional` 作参数或字段。
- 避免布尔模式标志让一个方法跑不同用例；优先拆成意图明确的方法。
- 普通同步用例方法从租户上下文取 `tenantId`；仅异步/回调/跨租户边界或解析上下文后的不可变事务命令显式传递。
- 重复的枚举展示名放枚举 `text` 属性，不写局部 `switch`。
- 删除本次重构引入的未用变量、导入、助手与陈旧分支。
- 命名表达业务结果，避免 `handle`、`processData`、`current`、`result` 等含糊名。
- 不重复通用包装（如 `withActivityLock`）；扩展现有基础设施组件。
- 重试有界；成功返回与重试耗尽异常都显式，不把终止藏进无界循环。

不为行数最少优化，为 reviewer 同时持有的概念数最少优化。

### 拒绝伪提取

不要仅因代码重复、视觉冗长或能起名就提取私有方法；只有新方法至少创造一个真实边界：

- 隔离可独立解释的业务规则或不变量
- 集中多个调用方共用的同一语义策略
- 分离不同职责（校验、查询、加锁、事务、投影）
- 拥有稳定失败、审计、兜底或副作用边界
- 实质性降低嵌套或调用方持有的概念数

以下为提取坏味道，优先保持内联：

- 只有一个调用方且仅转发到另一方法
- 只为补齐调用点已有参数而存在的重载
- 接收四个及以上调用方算好的值，只做格式化/日志/构造/转发
- 调用方仍持有起止（如计时开始在外、助手只算耗时）
- 只包装一条普通成功日志、一个平凡返回表达式或一次构造调用
- 减少调用方行数但增加参数传递、导航或命名负担

日志相关：

- 不为包装普通 `info` 查询成功日志建私有助手
- 常规查询耗时优先交给 APM、访问日志与慢 SQL 监控，不给每个读路径加业务 `info` 日志
- 仅当多个分支发出同一有意义业务事件，或助手拥有级别选择、限频、审计、兜底、脱敏、异常构造时才保留日志助手
- 计时范围要明确：记录 SQL 时间还是完整用例时间，不要把局部耗时标成总耗时

提取或保留助手前自问：

1. 这个方法拥有的策略或不变量是什么？
2. 没有它，改这个策略是否要改多个调用点？
3. 它减少的概念是否多于引入的参数与导航？
4. 名字能否描述领域步骤，而不是 `logQuery`、`handle`、`process` 这类实现动作？

答案不清晰就保持内联。不要用上下文 `record`、工具类、模板方法、AOP 或策略来掩盖伪助手的参数表。

## 5. 转换不进编排

- 重复的 DO/VO/DTO 转换复用现有领域 MapStruct 组件。
- 派生状态、名称、聚合等非 DO 事实通过显式不可变上下文传递。
- MapStruct 表达式保持确定性：转换器里不调 Mapper、远程 API、当前时间或安全上下文。
- 一次性简单同构复制用直接构造或 `BeanUtils`，转换器没有复用或清晰度收益时不新增。
- 大型持久化快照先由 `rule`/`transaction` 计算资格、期限、状态流转与调度，MapStruct 只拷贝已决定的值，不成为规则所有者。

## 6. 克制使用工具类

- 新增助手前先查既有 `util`、领域 `support` 与依赖。
- 新增领域专用远程 client 前先搜项目是否已有同一远程 API 的通用门面；复用并保留其显式失败模式，不为单次查询重命名加第二层包装。
- 重复的领域协议正则与长度上限放一个领域常量类：校验注解用编译期 `String`，运行时校验用预编译 `Pattern`。
- 复用 Hutool、Apache Commons 或 Spring 字符串助手做 trim/blank/null 归一，不造仅复刻 `trim`/`trimToNull`/`hasText` 的助手。
- 业务时钟负责当前时间与区转换；活动日期规则留在活动规则里。
- 安全随机码机制放 `util`（领域无关）；领域前缀、重试、唯一索引冲突处理留在领域 service/support。
- 工具类不得隐藏租户切换、权限、事务或业务失败语义。
- 单点本地化投影直接复用 Spring `MessageSource`；仅当至少两个调用方共享真实参数/兜底/键映射策略时才加领域 i18n 包装，单方法直通不构成抽象。

## 7. 为维护者写注释

新 Java 类型按项目中文类 Javadoc 写职责、作者、日期、版本。

DO、配置属性类、枚举有新增或实质变更时：

- 说明持久化/配置字段中不显而易见的快照、单位、可空、状态码、重试、期限含义
- 说明枚举常量与存储 `code`/展示 `text`
- 注释语义化且稳定，不复述字段名

接口：

- 每个公开方法写成调用方契约
- 说明参数、返回/缺失语义、异常、副作用、幂等、事务与锁前置条件

核心实现方法：

- 超过 10 行或拥有非平凡业务边界时补 Javadoc
- 解释步骤与顺序为什么存在，不复述语法
- 在租户忽略/复检、锁顺序、CAS 谓词、包含式时间边界、竞态收口复检、部分成功事务边界处加行注释
- 注释贴近其保护的不变量

不复述平凡赋值、不重复方法名、不写评审历史、不留与代码不符的陈旧注释；同一改动里更新或删除。

## 8. 复核清单

- 每个改动类能否用一句话概括职责？
- 每个依赖是否在允许方向？
- 用例服务是否主要是编排，而不是映射/查询/工具代码？
- 复杂 SQL 与 UI/查询策略是否在正确边界？
- 可复用上下文是否不可变并位于最窄共享层？
- 方法是否意图明确，无未用状态或伪抽象？
- 每个提取的助手是否拥有真实规则/职责/重复语义策略/失败边界，而非仅仅移动行？
- 单行日志包装、参数搬运助手、便利重载是否已删除（除非保护有意义事件或不变量）？
- 注释是否解释不变量与失败语义？
- 测试是否镜像生产包并针对提取后的职责？
